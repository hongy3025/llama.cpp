# GGSD 256-Token Segment Migration Plan

## Goal

Reduce GGSD segment granularity from 1024 tokens to 256 tokens for standard and hybrid split paths, with consistent hashing, file validation, KV slicing, server alignment, tests, and documentation.

## Decisions

- Use a single shared `llama_ggsd::SEGMENT_TOKENS = 256` constant for core GGSD and cache-GC code.
- Bump the GGSD on-disk version from 1 to 2. Existing 1024-token segment/session pools are intentionally invalidated rather than interpreted as 256-token objects.
- Keep `--prompt-cache-ssd-min-prefix` independent from segment size. Standard GGSD still restores only complete 256-token segments; hybrid `rec` snapshots remain non-aligned.
- Replace server hard-coded 1024 alignment and token-count reporting with the shared GGSD constant.
- Update tests to assert behavior at 256-token boundaries, including partial-cache and differential restore paths.

## Implementation

1. Update `src/llama-ggsd.h` constants and remove duplicate local constants from `src/llama-state-incr.cpp`.
2. Ensure all core save/load, hybrid split, quota validation, and server alignment paths use the shared constant.
3. Update GGSD test expectations and add a threshold/boundary assertion that distinguishes 256 from 1024.
4. Update GGSD guides and server documentation, including pool invalidation after the format-version change.
5. Build the affected targets, run GGSD tests, and exercise the server help/configuration path.

## Compatibility

This is an on-disk format migration. Old `seg`/`rec` objects and session hints must be removed or regenerated because their version is 1 and their segment hashes were constructed with 1024-token blocks.
